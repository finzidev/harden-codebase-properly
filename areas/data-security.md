# Data, security, migrations, integrations

Principle: **verify permissions on the database, not in the repository; exercise channels live — never infer one from the channel next to it.**

## Target state

### Modeling
- [ ] An **external source** flows in one direction only; the reverse direction is removed from the code, not switched off with a flag.
- [ ] Unsubscribe ≠ deletion ≠ "removed at the source": three events, three effects.
- [ ] Consent is **read**, never inferred: an absent state means "we don't know," never a no.
- [ ] Personal-data deletion suppresses durably via a **hash**, anonymizes dependencies, and re-admits only on confirmation; the export scope and the deletion scope must match.
- [ ] Tombstones and a trash bin: permanent deletion **only from the trash**.
- [ ] "Not a duplicate" is a fact (who, when), and it is revocable.
- [ ] Numbers get counted; write "—" when unknown, never 0; a cap declares `truncated`.
- [ ] Attributes get promoted to real columns once something filters or sorts on them.
- [ ] Dates are compared as **instants**, never as re-read strings.

### Security
- [ ] An env module with **fail-fast** startup in production: presence, "not the placeholder," mutual consistency.
- [ ] Secrets are **distinct per purpose** (data signing, session), required, and different from one another.
- [ ] Secrets stay server-side only; a clean secrets scan.
- [ ] **Deny-all row-level security** on every table, no policy for the API roles (`anon`, `authenticated`) until real database identities exist; verified with `sql/verify-permissions.sql` run as the API roles `[ASVS 5.0 V8.2.1]`.
- With grants held by `service_role` and the data layer on the service key, RLS is a perimeter against direct API access; it is never evaluated on the request path. Object-level authorization lives in the action.
- [ ] Grants on every sensitive function **verified on the database** after every schema deploy.
- [ ] Every action that takes an identifier from the client proves ownership or scope on the object before acting; the read that proves it and the read that acts are the same read `[OWASP API1:2023]`.
- [ ] Every public entry point (action, route handler, webhook, URL parameter) parses its input against a declared schema before first use; a parse failure is a readable rejection, never a coerced value `[ASVS 5.0 V2]`.
- [ ] Return values to the client are filtered to what the screen needs, never the raw row.
- [ ] Security headers set in one place and asserted by a test: CSP with `frame-ancestors`, `Strict-Transport-Security`, `X-Content-Type-Options`, `Referrer-Policy`; session cookies `HttpOnly`, `Secure`, `SameSite` `[ASVS 5.0 V3]`.
- [ ] No client-controlled value reaches a redirect target, an outbound fetch URL or an HTML sink (`dangerouslySetInnerHTML` and equivalents): grep = 0 or each hit justified.
- [ ] Uploads, where they exist: declared type and size limit, stored outside the served root, served with a fixed content type, filename never a path.
- [ ] A dependency audit in the verify chain: zero High/Critical or each with a ruling and a date; lockfile committed, `ci`-style install, CI actions pinned to a commit, workflow token read-only; an SBOM generated by a command and handed over `[OWASP Top 10:2025 A03; NIST SSDF PW.4.4]`.
- [ ] Signed tokens with a **separated rejection cause** (unreadable / invalid signature / expired), signature verified before every query `[ASVS 5.0 V9.1.1]`.
- [ ] Online, the entity read from the database decides, and it can only **narrow** what the token allows, never extend it past the token's own expiry `[ASVS 5.0 V9.2.1]`; offline, the token decides.
- [ ] Test and reset endpoints disabled by default, with a check that they are absent in production.
- [ ] Every defense **fails closed**: if the guard, the rate limiter, or the token check errors, it denies; never "let it through when unsure." One test per defense that simulates the failure and verifies the rejection `[ASVS 5.0 V16.5.3]`.
- [ ] Rate limiting on every authentication endpoint, or any endpoint that enumerates identities, with the policy **decided and written down** (per IP or per person, grace allowance, threshold on a shared gate) `[ASVS 5.0 V6.1.1]`.
- [ ] An access-revocation runbook with a "what it hits, what it doesn't" table (changing a password does not revoke a signed cookie; rotating the session secret does).
- [ ] Every secret has a written home (where it lives, who can read it) and a rotation trigger (a date or an event), rehearsed once like restore.
- [ ] A leaked-secret procedure in the revocation runbook, order fixed: revoke, rotate, purge, then look for what was done with it.

### Migrations and environments
- [ ] **Idempotent migrations** where the runner keeps no state (`if not exists`, `drop … if exists`); where the runner keeps state (Django, Rails, Alembic), replay proven on an empty database and a squash is a decision record; **never squashed** otherwise.
- [ ] Migrations applied and verified on the database **before** pushing the code that uses them; a destructive change is split in two: add and backfill before the code, drop after it `[Fowler & Sadalage, Evolutionary Database Design]`.
- [ ] Every migration carries its reverse in the same file, or a written line saying why there is none and what the recovery is instead (restore from backup, at what cost, with what data-loss window).
- [ ] **A single source-of-truth database**: CLI, MCP, and app point to the same project, verified before every write command.
- [ ] Every function rewrite starts from the **latest** definition and **reasserts the grants**.

### Integrations and operations
- [ ] Automated backup with verification of **arrival** (one row per run, written by the last link in the chain), not of departure.
- [ ] Restore tested end-to-end at least once with a count comparison; if not done, **declared** as tech debt.
- [ ] Every channel (email, alerts, dead-letter, sync) exercised live with an **injected failure**.
- [ ] Structured logs with no personal data; alerts guarded against an alert that stays permanently stuck on `[ASVS 5.0 V16.2.5]`.
- [ ] A request id generated at the edge, carried through every log line of the request and returned as the support id on screen: one grep proves the same id reaches both.
- [ ] A written list of the events that must be logged (authentication outcome, authorization refusal, irreversible action, permission change, migration applied) with actor, object, instant `[ASVS 5.0 V16]`.
- [ ] Log retention and alert routing decided and written (who is woken, after how many, how long logs are kept), in `MONITORING.md`.
- [ ] Every webhook is idempotent (same event twice, one effect) and every external call carries an idempotency key.
- [ ] A write and its outgoing event are one transaction (outbox) and reconciled on a schedule `[Helland, CIDR 2007]`.
- [ ] Post-write navigation happens server-side (`redirect()` inside the action, after invalidations), never a client push after a server action.

## What to measure

1. **Env**: is there a single module? What happens in production with a missing variable, or one equal to the example placeholder?
2. **Policies**: from the database, not from the repository; read the predicate of every policy, never only its presence.
3. **Grants and policies, one file**: run `sql/verify-permissions.sql` (shipped with this skill) as `anon` and as `authenticated`, never as the owner: owners and `bypassrls` roles are not subject to RLS `[PostgreSQL ddl-rowsecurity]`. It prints every function's ACL with a null ACL spelled out as `DEFAULT: PUBLIC CAN EXECUTE` (a P1, not a pass), every table's `relrowsecurity`/`relforcerowsecurity`, and every policy with its `qual` and `with_check`. Read the predicate, not the count: `using (true)` is a policy and a hole.
4. **Migrations**: headers read by family (policies, grants, indexes, functions, tombstones, promoted columns); did a function rewritten several times start each time from the latest definition?
5. **Environments**: compare the CLI's project reference against the app's env host.
6. **Secrets**: run a scan (gitleaks or equivalent); check for public variables that contain keys.
7. **Tokens**: does verification distinguish the three outcomes? Is a revoked entity admitted because the token says yes, or an expired token admitted because the database is reachable?
8. **Channels**: for each one, the date of the last live test and how arrival was confirmed.
9. **Backup**: how is success determined — from the last link in the chain, or from the first HTTP 200?
10. **Dates**: where are re-read strings from the database being compared (`!==` between timestamps)?

## Rules with mechanical verification (specified here; `sql/` ships the queries, the brief builds the rest)

- No sensitive function is executable by the API roles: `sql/verify-permissions.sql`; **a null `proacl` means default privileges (world-executable), not clean** `[PostgreSQL ddl-priv]`.
- `revoke … from public` **is not enough on Supabase**: `anon` and `authenticated` hold their own grant (the project grants all on functions to them by default privileges). Revoke from `public, anon, authenticated`, and `alter default privileges … revoke execute on functions from anon, authenticated`, once per grantor role: a default-privileges entry belongs to the role that created it `[PostgreSQL ALTER DEFAULT PRIVILEGES; supabase/postgres init SQL]`.
- **A function dropped and recreated, or recreated with a new signature, starts from default privileges** (`create or replace` of the *same* signature keeps the ACL `[PostgreSQL 12–18]`): reassert the grants in every migration that touches the function, and verify afterward.
- Rewrite from the latest definition: grep every migration that touches the function, diff against the most recent one.
- The app refuses to start without secrets: a test that boots with `NODE_ENV=production` and a missing variable.
- A migration run twice does not fail: an idempotency test.
- Dates as instants: dedicated helpers, a test on both literal forms (`+00:00` and `Z`); the fake does not reproduce the defect because it has no real columns.
- Backup success read from the run row (`finished_at`, `complete`, `errors` empty).
- CLI on the same database as the app: compare before every write command.

## Known traps

- **`revoke from public`** that leaves `anon` and `authenticated` holding their own explicit grant.
- **`drop function` + `create`, or a changed argument list**: a new function with default privileges, the same function closed off, over and over.
- **A guard that authenticates and never authorizes**: the action checks the session, then reads by the id the client sent.
- **RLS believed to cover the request path**: deny-all policies, and every read on the service key — the policies are never evaluated.
- **A schema on the form and none on the action**: the browser validates, the direct POST does not.
- **Rebuilding from an old version**: a silent regression, a column goes back to NULL with no error.
- **Code deployed before the migration**: the adapter sends every field, the database rejects the whole write.
- **CLI connected to the wrong project**: `db push` succeeds and reports success.
- **An email provider that rejected an empty array** (`tags: []`) *(seen once, one provider, origin project; not in any vendor doc)*: only the message family missing that field failed, the alerts, while real emails hid it. Omit the field when empty; test the alert channel live.
- **A timestamp re-read in a different form**: `!==` between the database's `+00` and JavaScript's `Z` is true for the same instant `[RFC 3339 § 4.3]`; compare instants.
- **A revoked entity still admitted online** because the copy inside the token says yes; never an expired token admitted because the database is reachable.
- **Changing a password, expecting it to revoke sessions**: the cookie is signed, not checked against the password.
- **`router.push()` after a server action**: navigation lost, intermittently *(observed in the origin project; the documented path is `redirect()` inside the action)*.
- **An event emitted after the commit that never happened**, or a commit whose event never left: the outbox is the fix; the reconciliation is the proof.
- **An unexpected foreign-key cascade** during a remediation pass: stop and ask.
- **A "succeeded" from the first link** in the backup chain, while the last one never arrives.
- **A defense that fails open**: a `catch` around the rate limiter or guard that lets traffic through on failure, "so as not to block users." On failure: deny, and alert.
