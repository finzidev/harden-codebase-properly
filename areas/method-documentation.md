# Method and documentation

Principle: **documentation stays true because it is checked against the product, not against the writer's memory.** A number lives in one place. A decision carries its rejected alternatives. A debt item carries its trigger.

## Target state

- [ ] A **decision register** (`docs/decisions/`), one decision record per reversible choice, six parts, including rejected alternatives. Format: `../templates/decision-record.md`. Started **in the first week**, not the ninth: whatever gets reconstructed later from commits and migrations should have been written once, the first time.
- [ ] An **index** (`docs/INDEX.md`) as the single entry point, with counts regenerated by **counting files**.
- [ ] **A number lives in one place**; every other document links to it.
- [ ] An **acceptance checklist** ("does it work?") kept separate from the **work register** ("we're fixing it, how?"), linked by one mechanical field; automated checks for coverage, stale wording, and phrases found again.
- [ ] Three lists in acceptance testing (to review / to recheck / closed), never a filter on the same list; the register — not a status color — decides who has "taken it on."
- [ ] A **user guide** generated from a single source (the same one the in-app guide uses), searchable **by intent** (every step declares the words someone would search it with), with **real screenshots** or declared placeholders; coverage measured against real routes.
- [ ] **Feature** records (what a screen does today, with a freshness note) and **use-case** records (the same paths, seen from the actors' side).
- [ ] **Architecture** docs rewritten against the real code; **maintenance** docs carrying the measurements (dead code, centralization, boundaries).
- [ ] Operational **runbooks**: backup and restore, monitoring, access revocation.
- [ ] A **tech-debt register** with origin, destination, priority, and trigger; every marker in the code has a matching line.
- [ ] **Client questions** live in one place, split by audience: product questions (a table inside the decision register) and organizational ones (`docs/client/`); never merged; internal questions never make it into a client meeting.
- [ ] **Handover minutes** as records that never get edited after the fact; an ownership-transfer plan.
- [ ] Commits written in the host project's language, stating the **effect** on the user or the data and the why, not the implementation.

## Reference map

| Folder | Role |
|---|---|
| `decisions/` | why it was done this way: the only folder with rejected alternatives |
| `features/` | what every screen does today |
| `use-cases/` | the same paths, seen from the actors' side |
| `architecture/` | how, technically, checked against the real code |
| `maintenance/` | code health, measured |
| `acceptance/` + checklist | current work |
| `guide/` | user manual, generated |
| `operations/` | runbooks |
| `planning/` | tech debt with triggers |
| `client/` | organizational questions for the client |
| `handover/` | minutes and the transfer plan |
| `project/` | scope and stories |
| `commercial/` | contract and quotes: never edited |
| `archive/` | finished plans, kept as memory |

These are defaults: if the host project already has a docs language and folder convention, use it (the stack map records it).

## What to measure

1. Does a decision register exist? How many reversible choices from the last few months have no decision record? (Read the commits: every "was X, now Y" with no record is a candidate.)
2. Does the index count files, or just recall them? How long has it been stale?
3. Which numbers appear in more than one document? (grep for the number.)
4. Is the acceptance checklist a partition of the code's surface, or an eyeballed list?
5. Does the guide name screens or commands that no longer exist? Which routes does it not describe?
6. Is the debt written down somewhere, with the condition that reopens it?
7. Do client questions live in chat, scattered across files, or in one place?
8. Do the last twenty commits state the effect, or the implementation?

## Document and commit style

Documents, reports, decision records, and checklists are written in the host project's language; these instructions are in English.

Impersonal voice; the subject is the effect on the user or the data; one sentence in two beats (what changes, then why or the flip side); no jargon in the title; documents quote the reporter's exact words, because a summary is already interpretation.

Commit messages follow the host project's language; the shape is `fix(area): <what changes for the user>, <why or the flip side>`. Example shapes: "the alerts weren't firing, and never had been"; "the count is done by the database now, and the loop sits above the guard"; "a single table, filterable across the whole management system"; "a facet error stops disguising itself as 'there's nothing here.'"

## Rules with mechanical verification

- Decision record number: the first free one, found by **listing the whole folder**, never `ls | tail -1` (collides across parallel sessions).
- Counts printed into documents by a script, never typed by hand.
- Checklist as a partition of the surface: a coverage script at zero gaps and zero phantom entries.
- No entry describes a changed gesture: a stale-wording script catches it.
- Every phrase from an acceptance round is found again in the register: a script compares head and tail.

## Known traps

- **A decision register started too late**: weeks of reconstruction from commits and migrations.
- **A stale index** lying about the folders: regenerate it by counting.
- **A number in nine files**: wrong in all nine within a day.
- **An audit applied in the same round** it was written in.
- **"Not done" claimed from memory** on a repository with multiple sessions.
- **`git stash` used for A/B** on a shared tree: use one file with `cmp`, or a `git worktree`.
- **An automated "dead link" check** on the documentation: confuses a deleted page with a dynamic route id; tried and dropped — the debt stays declared, with its trigger.
- **No decision record for a non-decision or a rejected proposal**: the register is the only place they don't get lost.
